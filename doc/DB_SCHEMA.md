# DB_SCHEMA.md — Meeting-AI

> Source: db/schema.ts (Drizzle). Task-loaded: read when the task touches
> the DB. If you change it, also read MIGRATIONS.md.

## Tables

### user / session / account / verification
Managed by better-auth. Do NOT edit by hand — this is the structure the
auth library expects. Must stay in sync with auth-schema.ts.

### agents
An AI agent created by a user.
- id (nanoid, PK)
- name (not null)
- userId -> user.id (cascade delete)
- instructions (not null) — the agent's AI prompt
- createdAt, updatedAt

### meetings
- id (nanoid, PK)
- name, userId -> user.id (cascade)
- agentId -> agents.id (cascade)
- status: enum ["upcoming","active","completed","processing","cancelled"]
- startedAt, endedAt (nullable)
- transcriptUrl, recordingUrl (nullable) — come from Stream
- summary (nullable) — generated by AI (Inngest)
- createdAt, updatedAt

## Important relationships
- meeting -> agent (required). If the agent is deleted, its meetings go too.
- meeting.status drives the flow:
  upcoming -> active -> processing -> completed (or cancelled)
- summary/transcriptUrl only fill in after "completed".

## Watch out
- All IDs are text + nanoid, NOT auto-increment.
- FKs use onDelete: cascade — deletes chain. If you add a new relation,
  think through the cascade effect (unexpected data loss).
- summary is text — no length limit, but an AI summary can be large.
  Account for length in the UI.
